## 1. سبب فتح P151

أثبت P150 أن Service Worker يستطيع:

- التفعيل الفوري؛
- السيطرة على النوافذ؛
- إعادة تحميل النوافذ عند activation؛
- استخدام cache namespace مرتبطًا بإصدار SW؛
- منع cache للـHTML/API/runtime code.

لكن المراجعة الجنائية اكتشفت فجوة مهمة: `Current/PWA/New-main` لا يحمّل `register-sw.js` المشترك، بل يسجل `sw.js` inline.

وبالتالي كان polling الدوري الموجود في `register-sw.js` لا يضمن الوصول إلى New-main.

## 2. الحل النهائي P151

بدل تعديل `New-main` الضخم والمحمّي، تم نقل مسؤولية الحقن إلى Service Worker نفسه.

عند خدمة HTML من خلال SW:

1. يجلب الـHTML من الشبكة.
2. يتحقق أن المحتوى HTML.
3. يتحقق من عدم وجود marker باسم `RAWAEA_UPDATE_COORDINATOR`.
4. يحسب مسار `register-sw.js` انطلاقًا من `self.registration.scope`.
5. يحقن:

```html
<script id="RAWAEA_UPDATE_COORDINATOR" src="<scope>/register-sw.js"></script>
```

قبل `</head>`.

بهذا يصبح `New-main` خاضعًا لنفس Update Coordinator دون إعادة كتابة الملف الكبير.

## 3. دورة التحديث بعد P151

```text
Git/PWA release
      ↓
new sw.js served
      ↓
registration detects new SW
      ↓
install → skipWaiting()
      ↓
activate → delete old cache
      ↓
clients.claim()
      ↓
reload in-scope windows
      ↓
HTML served through new SW
      ↓
register-sw.js injected
      ↓
update() immediately + every 60s + visibility + online
      ↓
future SW updates detected automatically
```

لا يوجد اعتماد على Cache Clear يدوي.
ولا يوجد اعتماد على ضغط المستخدم على زر تحديث.
