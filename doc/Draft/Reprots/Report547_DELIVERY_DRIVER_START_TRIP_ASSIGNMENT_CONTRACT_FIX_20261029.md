# Report547 — إصلاح رفض بدء رحلة مندوب التوصيل بسبب اختلاف حقل الإسناد

**التاريخ:** 2026-10-29  
**النوع:** تحقيق جنائي، إصلاح Production محدود لدالة قائمة، وتثبيت المصدر المرجعي.  
**النطاق:** فشل `start-delivery` برسالة «هذا الرانشيت معين لسائق آخر» رغم ظهور الرانشيت للمندوب نفسه.  
**الحالة:** `ROOT CAUSE CONFIRMED / EXISTING EDGE FUNCTION V8 DEPLOYED / CANONICAL SOURCE COMMITTED / LIVE BUSINESS E2E NOT RUN / NOT CLOSED`

## 1. استعادة السياق وحوكمة التنفيذ

- تمت قراءة `CURRENT_STATE.md` وReport545 وReport546، مع احترام قاعدة التعديل الجراحي: إثبات السبب من الكود والبيانات الحية، تعديل المسار المسؤول فقط، عدم إنشاء Edge Function جديد، عدم اصطناع تكليف أو تعديل حالة رانشيت بغرض الاختبار، وعدم اعتبار نجاح النشر مساويًا لنجاح E2E.
- مرجع المالك حول ملكية ملفات التشغيل محفوظ في Report545. التعديل الحالي يخص دالة Backend قائمة ومسموح بإصلاحها مباشرةً؛ لم أعدّل `companies/company-1/delivery/driver.html` أو `main.html`.
- تم فحص تعريف الدالة الحي قبل التعديل، ثم إعادة قراءته بعد النشر، مع الحفاظ على `verify_jwt=true`.

## 2. الأدلة المؤكدة

### 2.1 سجل Production

استعلام قراءة فقط على `RS-1` وحساب `driver@rawaea.com` أعاد:

| الحقل | القيمة |
|---|---|
| `runsheets.status` | `Loaded` |
| `runsheets.driver_id` | `NULL` |
| `runsheets.deliverer_id` | `0912a68e-a2d6-4e3a-b44d-41f8826fb900` |
| `public.users.id` للمندوب | `0912a68e-a2d6-4e3a-b44d-41f8826fb900` |
| تطابق `driver_id` | لا |
| تطابق `deliverer_id` | نعم |

هذا دليل مباشر على أن الرانشيت مسند إلى المندوب عبر `deliverer_id`، بينما `driver_id` فارغ. لا توجد حاجة لتغيير بيانات الرانشيت أو إعادة إسناده.

### 2.2 سبب الرفض في الدالة

نسخة Production السابقة من `start-delivery` (Version 7، SHA `7e87dd0a29d57d3d286c19e05aed70c8b40c7e74645fc73f593e6eee2610399e`) كانت:

1. تقرأ `driver_id` من الرانشيت.
2. تقارن `rs.driver_id` مع `public.users.id`.
3. ترفض الطلب برسالة «هذا الرانشيت معين لسائق آخر» عندما لا يتطابق الحقلان.

وهذا عقد خاطئ في هذا المسار: مصدر الإسناد الفعلي الذي أثبته سجل Production وسياسة قراءة المندوب هو `runsheets.deliverer_id`. لذلك فالرسالة لا تثبت أن الرانشيت مسند إلى شخص آخر؛ بل كانت نتيجة مقارنة العمود الخطأ.

## 3. الإصلاح الجراحي المنفذ

### الملف التنفيذي

- **الدالة القائمة:** `start-delivery` — لم تُنشأ دالة جديدة.
- **الإصدار السابق:** Version 7.
- **الإصدار المنشور:** Version 8.
- **SHA المنشور بعد الإصلاح:** `78fb8b6f4d70e55b1290b06f73e5581e2be7b7d34f6270c16384afe6c94966fa`.
- **التحقق بعد النشر:** أعادت قراءة Supabase الدالة بالإصدار 8 و`verify_jwt=true).

التغييرات المحدودة:

1. قراءة `deliverer_id` بدلًا من `driver_id` عند التحقق من تكليف الرانشيت.
2. رفض بدء الرحلة فقط إذا كان `deliverer_id` لا يطابق هوية سجل المستخدم الفعلي.
3. تضمين نفس شرط الإسناد في UPDATE نفسه، إلى جانب الشركة والحالة `Loaded`، لتقليل خطر تغيير التكليف/الحالة بين القراءة والتحديث.
4. فحص الصف المعدل فعليًا؛ إذا لم يعد الصف يطابق الشروط، ترجع رسالة واضحة تطلب تحديث التطبيق والتحقق من التكليف.
5. إبقاء تسجيل قراءة العداد في `vehicle_tracking.driver_id` كما هو؛ هذا حقل سجل تتبع وليس مصدر إسناد الرانشيت.

## 5. الفصل بين الإشارات في Console

- `POST /functions/v1/start-delivery 400`: السبب الجذري المؤكد هو فحص حقل الإسناد الخاطئ كما هو موضح أعلاه؛ تم نشر الإصلاح.
- `POST /auth/v1/token?grant_type=password 400`: هذه استجابة مصادقة مستقلة عن فحص إسناد الرانشيت. لا يتوفر جسم الاستجابة أو دليل كافٍ للجزم هل السبب كلمة مرور غير صحيحة أو حالة حساب أو سبب آخر؛ تبقى `UNKNOWN` ولا ينبغي خلطها بعطل `start-delivery`.
- تحذير Tailwind CDN و404 للـfavicon لا يفسران رفض بدء الرحلة، ولا توجد حاجة لتعديلهما ضمن هذا الإصلاح.

## 6. فجوة مستقلة اكتُشفت ولم أخلطها بالسبب الجذري

حقل اختيار صورة العداد ظاهر في `driver.html`، لكن `preConfirm` يعيد `meter_reading` فقط، وطلب `start-delivery` يرسل `runsheet_code` و`meter_start` دون ملف الصورة. كما يوجد `vehicle_tracking.meter_photo_url` في قاعدة البيانات، لكن لم يظهر عقد تخزين خاص موثق ومناسب لأدلة عداد المركبة. مخزن `product-images` عام، ومخزن `employee-documents` خاص بسياسات HR/الموظف؛ لم أستخدم أيًا منهما بطريقة غير معتمدة، ولم أفتح وصولًا عامًا لصور المركبات.

**الحالة:** `CONFIRMED GAP / NOT FIXED IN THIS CHANGE`. يلزم قرار/عقد تخزين خاص بأدلة المركبات وصلاحيات قراءتها، ثم Patch جراحي منفصل للواجهة والدالة. هذا لا يغيّر تشخيص رفض بدء الرحلة الحالي.

## 8. الحكم النهائي وخطوة الإغلاق

**ما ثبت:** سبب رسالة «هذا الرانشيت معين لسائق آخر» هو مقارنة `driver_id` بدل `deliverer_id`. الإصلاح منشور في الدالة القائمة، ومصدره محفوظ في GitHub.

**ما لم يثبت:** أن التطبيق المنشور يستدعي الإصدار الجديد بنجاح من جلسة مندوب مصادق عليها، وأن رحلة حقيقية تبدأ وتنتقل إلى شاشة الأوردرات دون تكرار.

**الخطوة التالية الدقيقة:** افتح تطبيق المندوب في جلسة جديدة/تحديث قوي، وسجّل الدخول بحساب المندوب المخوّل، ثم جرّب بدء `RS-1` بقراءة عداد حقيقية. إذا نجح، تحقق من الحالة `Delivering` وسجل `vehicle_tracking` الناتج عن العملية الطبيعية، ثم وثّق Console/Network بعد تنقيح الرموز السرية. لا تعِد محاولة البدء إذا تحولت الحالة إلى `Delivering` بالفعل. إن استمر الخطأ، سجّل جسم استجابة `start-delivery` وحالة HTTP دون مشاركة Authorization أو cookies.
