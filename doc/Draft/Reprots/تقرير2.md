# تقرير2 — P135 Forensic Runtime Repair

## Evidence
- `Current/PWA/New-main` is the target artifact.
- Supabase project is healthy and the source contains the current active key; no key rotation was performed.
- Browser error `MAIN11_SUPABASE_UNAVAILABLE` is caused by an incorrect availability guard checking the UMD namespace instead of the instantiated local client.
- Browser `401 Invalid API key` remains a separate deployment/artifact-lineage issue because the source target carries the active configuration while Supabase also records successful requests from another runtime.

## Surgical repair
Replaced the MAIN11 guard matching `!window.supabase || !supabase.auth` with:

```js
if (typeof supabase === 'undefined' || !supabase || !supabase.auth) {
```

Added a non-secret runtime marker:

```js
window.__RAWAEA_P135_RUNTIME_BUILD__ = 'P135-2026-09-01';
console.log('RAWAEA_P135_TARGET', 'New-main');
```

The Supabase URL/key and login function were not changed.

## Verification
The inline runtime is syntax-checked with Node before commit. Final closure requires the deployed browser to show the P135 marker and then a successful login. If marker appears but 401 remains, the investigation moves to the served artifact/client configuration. The Service Worker 404 remains a deployment routing/root question and is not changed speculatively.

## Previous executor failure
The existing Gold/Diamond executor failed with `P135_EXPECTED_GUARD_NOT_FOUND` even though a fresh direct read of the same target blob showed the defective guard still present. That executor failure is recorded as an execution-path defect, not evidence that the source was fixed.
