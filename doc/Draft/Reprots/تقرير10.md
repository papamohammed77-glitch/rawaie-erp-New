### Original/register-sw.js

- `skipWaiting()` أثناء install.

- تنظيف الكاش القديم.

المبدأ التشغيلي التاريخي الصحيح هو أن الـHTML/API لا ينبغي أن يظل محبوسًا داخل cache قديم، وأن الـSW الجديد يجب أن يصبح active دون انتظار tab قديم.

## 4. العيب المكتشف في Current

`Current/PWA/New-main` لم يكن يستخدم `register-sw.js` المشترك أصلًا.

بل يحتوي داخل نفسه على تسجيل مباشر:

```javascript
if('serviceWorker'in navigator)
  navigator.serviceWorker.register('./sw.js',{scope:'./'})
    .catch(...)
```

ولم يثبت داخل هذا المسار:

- polling كل 60 ثانية؛
- `visibilitychange` update checks؛
- auto reload عند `controllerchange`.

لذلك كان سلوك Current أضعف من العقد التاريخي في جانب **continuous update detection**.

الأهم أن Current `sw.js` كان عند النسخة `2.2 FINAL` مع:

```text
STATIC_CACHE = rw-static-v3
SW_BUILD = RAWAEA_SW_P137_FINAL
```

وبالتالي ظل اسم الكاش ثابتًا بين إصدارات الـSW، وهو ما يسمح نظريًا ببقاء static presentation assets قديمة إذا تغيرت محتوياتها مع بقاء نفس cache namespace.

## 5. الحل المعتمد P150

تم تصميم الحل على مستويين بدل ترقيع سطر واحد:

### A — Service Worker identity is versioned

تم تغيير الـcache namespace إلى:

```javascript
var SW_BUILD = 'RAWAEA_SW_P150_AUTO_UPDATE';
var STATIC_CACHE = 'rw-static-' + SW_BUILD;
```

وبذلك كل إصدار SW جديد يحصل على cache namespace مستقل.

### B — Immediate activation

تم الإبقاء على:

```javascript
self.skipWaiting()
```

ليصبح الإصدار الجديد active فور تثبيته.

### C — Claim all in-scope clients

تم الإبقاء على:

```javascript
self.clients.claim()
```

ثم إضافة آلية إعادة تحميل تلقائية للنوافذ الواقعة داخل scope.

### D — Automatic client reload

عند activation جديد، يتم جمع النوافذ داخل `self.registration.scope` ثم تنفيذ:

```javascript
client.navigate(client.url)
```

وبالتالي لا توجد حاجة إلى زر "تحديث الآن" بعد وصول إصدار جديد.

### E — Network Only للـHTML / API / runtime code

تم الحفاظ على:

- HTML/navigation = Network Only
- Supabase/API = Network Only
- `.js/.mjs/.ts` = Network Only

وهذا يمنع runtime code أو application shell من التجمّد على نسخة قديمة.

### F — تحديث المشترك

تم تحديث `register-sw.js` في Current وPublished ليشمل:

- update check فوري؛
- update check كل 60 ثانية؛
- update check عند visibility؛
- update check عند online؛
- reload تلقائي عند `controllerchange`.

هذا يعيد السلوك التاريخي ويجعله أقوى من ناحية عدم انتظار موافقة المستخدم.

## 11. أخطاء وتجارب سابقة يجب تسجيلها

### الخطأ 1 — تفسير 401 على أنه Supabase Key defect

تم رفض هذا الاستنتاج بعد إثبات أن المفتاح الموجود في Current وPublished Git هو نفسه المفتاح النشط في Production.

### الخطأ 2 — اعتبار P146 Git commit دليل Production runtime

تم تصحيح هذا المفهوم؛ Git update ليس دليلًا على أن Worker serving layer استهلك commit.

### الخطأ 3 — الاعتماد على banner/manual reload

هذا لا يطابق مطلب المالك "لا أريد Cache Clear ولا إجراء إضافي للمستخدم".

P150 نقل السلوك إلى automatic reload.

### الخطأ 4 — إبقاء cache namespace ثابتًا

هذا لا يضمن refresh حقيقي للموارد الثابتة عند تغيّر الإصدار.

تم تحويله إلى versioned cache namespace.

### الخطأ 5 — اعتبار `register-sw.js` الحالي مستخدمًا فعليًا في New-main

ثبت عكس ذلك؛ `New-main` يسجل الـSW inline ولا يحمل الملف المشترك.

ولهذا تم تحديث الـSW نفسه ليحمل auto-reload behavior، حتى لا يعتمد النظام على ملف لم يثبت أنه loaded.
