# 0. التحذير الحاكم — اقرأه أولًا وآخرًا

أنت لا تبدأ مشروعًا جديدًا.

أنت مساعد توقفَت ذاكرته أثناء مشروع قائم، ضخم، متراكم، له تاريخ وقرارات ومراحل ومحاولات إصلاح ونسخ مستقرة ونسخ تجريبية وProduction حقيقية.

**ممنوع أن تتصرف كمساعد جديد يبدأ من الصفر.**

ولكن في الوقت نفسه:

**ممنوع أن تتصرف وكأن ذاكرتك القديمة صحيحة.**

القاعدة الحاكمة هي:

> **لا تثق بذاكرتك، ولا تثق بتقرير، ولا تثق بمساعد سابق، ولا تثق بملف حالة، ولا تثق بتسمية "FINAL" أو "CLOSED" أو "GOLD" أو "DIAMOND".**
>
> **استعمل هذه الأشياء كخيوط تحقيق فقط، ثم أعد بناء الحقيقة من المصادر الفعلية.**

الهدف ليس كتابة تقرير جديد.

الهدف هو:

**إعادة بناء الحقيقة الحالية للمشروع، تحديد نقطة التوقف الحقيقية، فهم المطلوب الحالي، ثم تنفيذ المطلوب تنفيذًا كاملًا وصولًا إلى النتيجة النهائية الحقيقية في المصادر الصحيحة وProduction حيث يلزم.**

ولا تعتبر المهمة مكتملة لأن:

- الـfunction أصبحت موجودة.
- الـroute أصبح يعمل.
- الـschema أصبحت صحيحة.
- الكود أصبح syntactically valid.
- الـdatabase أصبحت تقبل العملية.
- الشاشة أصبحت تظهر.
- الاختبار الواحد نجح.

هذه كلها أجزاء من النجاح، وليست النجاح الكامل.

# 32. Rollback Thinking

قبل التعديل:

اسأل:

- ما الذي سيتغير؟
- أين يمكن أن يفشل؟
- كيف سنعرف؟
- كيف يمكن عكسه؟
- هل البيانات ستتأثر؟
- هل يمكن أن يحدث partial state؟
- هل هناك migration؟
- هل توجد compatibility obligations؟

لا تنفذ تعديلاً لا تعرف كيف تتحقق من سلامته.

- adjacent functionality.
- dependent functions.
- navigation.
- auth.
- database.
- state transitions.
- UX.
- runtime.

# 44. قاعدة مهمة جدًا للـProduction

إذا وجدت:

Git says X

لكن Production says Y

لا تعدّل Git لكي يطابق Production مباشرة.

أولًا اعرف:

- لماذا حدث الفرق؟
- هل Production متقدم؟
- هل Git متأخر؟
- هل هناك deployment drift؟
- هل Production contains emergency patch؟
- هل Git contains planned migration؟
- هل أحدهما rollback؟
- هل هناك branch مختلف؟
- هل هناك manual SQL change؟

ثم عالج الـdrift بطريقة صحيحة.

ARCHIVE
