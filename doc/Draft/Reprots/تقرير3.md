# تقرير3 — P136 MAIN11 Supabase Scope Repair

## الحالة
تمت مراجعة P135 مباشرة من Git وSupabase وRuntime evidence. P135 أصلح نص guard فقط، لكنه لم يصلح JavaScript scope: MAIN11 يعمل داخل IIFE مستقل ولا يستطيع رؤية `supabase` المحلي المنشأ في MAIN1.

## Root Cause
`MAIN11_SUPABASE_UNAVAILABLE` كان نتيجة scope isolation، وليس دليلًا على أن Supabase key غير صالح. Supabase نفسه يحمل المفتاح النشط، وسجل Auth أثبت نجاح تسجيل دخول المالك من Runtime آخر.

## P136 Surgical Change
1. تم تصدير نفس Supabase client الموجود بالفعل إلى `window.RW_SUPABASE_CLIENT` دون تغيير URL أو key أو createClient options.
2. تم استبدال guard الخاص بـMAIN11 ليستخدم المرجع المشترك صراحةً:

```js
var sb = window.RW_SUPABASE_CLIENT || null;
if (!sb || !sb.auth) {
    console.error('MAIN11_SUPABASE_UNAVAILABLE');
    return;
}
```

3. تم تغيير `getSession()` في MAIN11 ليستخدم `sb`.
4. تم إضافة marker غير سري `__RAWAEA_P136_SCOPE_REPAIR__='shared-client'`.

## Verification
تم تشغيل `node --check` على كامل inline runtime ونجح قبل commit. لم يتم تغيير Supabase credentials أو بيانات Production أو Service Worker routing.

## P135 Executor Failure
المحاولة السابقة فشلت لأن executor استخدم مطابقة نصية ضيقة لصيغة `createClient`، لا لأن الإصلاح المقترح كان غير صحيح. لذلك عُدلت أداة التنفيذ إلى regex مقيد بالـclient declaration فقط.

## Closure Gate
تبقى `401 Invalid API key` غير مغلقة حتى يظهر marker P136 في Pages served artifact ويجتاز Login فعليًا. استمرار 401 بعد marker يعني أن مشكلة الـserved artifact/client configuration منفصلة عن source scope bug.
