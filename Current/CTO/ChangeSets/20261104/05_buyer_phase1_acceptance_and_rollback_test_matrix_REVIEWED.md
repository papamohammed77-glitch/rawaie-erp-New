# RAWAEA ERP — Buyer Phase 1
# مصفوفة الاختبارات والقبول والتراجع

**الحالة:** خطة اختبارات إلزامية؛ لم تنفذ بعد على قاعدة الإنتاج.  
**نطاقها:** PO invoice source / Quick Market Draft / Buyer goods custody / cash custody reservation / permissions / idempotency / no duplicate stock or AP.  
**سياسة بيانات الاختبار:** استخدام معاملات SQL تنتهي بـ `ROLLBACK` فقط. لا تترك فواتير أو أحداث حيازة تجريبية دائمة؛ لا تُحذف أحداث الدفتر بعد اعتمادها، بل تعالج بأحداث عكسية، لذلك لا نستخدم أحداث Production دائمة للاختبار.

---

## 1. بوابة ما قبل التنفيذ

لا يبدأ اختبار التنفيذ إلا بعد:
1. تثبيت نسخة ChangeSet واحدة من ملفات المخطط والوظائف والـEdge والواجهة والتراجع.
2. التحقق من جميع أسماء الأعمدة والقيود والتواقيع من Production لحظة التنفيذ.
3. إثبات أن جميع وظائف SQL الجديدة موجودة بالتواقيع الدقيقة، وأن `search_path` فارغ في وظائف SECURITY DEFINER الجديدة.
4. التحقق من أن وظائف Edge الحالية فقط هي التي ستتغير؛ لا يظهر أي slug جديد في Supabase.
5. التحقق من عدم وجود بيانات أو أحداث حيازة أو فواتير مصنفة جديدة قبل تشغيل الاختبارات.
6. أخذ لقطة counts وhashes قبل التغيير، ثم توثيقها في التقرير.

## 2. اختبارات SQL للبيانات والعقود

يُستخدم مالك/مستخدم مصرح به من نفس الشركة، ومورد نشط، وفرع صالح، وصنف نشط. لا تُستخدم سجلات فواتير الاختبار الحالية PINV-1000/1001/QA-SR في أي اختبار.

### 2.1 إنشاء فاتورة PO

| الاختبار | النتيجة المتوقعة |
|---|---|
| إنشاء PO invoice بمورد وPO من الشركة نفسها | Draft + `purchase_source=PURCHASE_ORDER` + EGP |
| PO لمورد آخر | رفض |
| PO بعملة غير عملة النظام | رفض |
| فرع من شركة أخرى | رفض |
| `purchase_order_id` فارغ في المسار العادي | رفض؛ يجب استخدام Quick Market |
| نفس operation_id ونفس payload | نفس الفاتورة، duplicate=true |
| نفس operation_id مع payload مختلف | تعارض ورفض |
| تعديل مسودة PO عبر العملية الجديدة | تعديل ذري وتحديث بصمة المصدر |
| تعديل PO invoice بعد استلام أو ترحيل أو مصروف تابع | رفض |

### 2.2 إنشاء Quick Market

| الاختبار | النتيجة المتوقعة |
|---|---|
| المورد النشط والفرع الصحيح والبنود الصحيحة | مسودة Quick Market |
| المورد غير نشط أو من شركة أخرى | رفض |
| لا يوجد فرع | رفض |
| لا يوجد رقم فاتورة المورد | يسمح بإنشاء المسودة فقط إذا اعتمدت السياسة؛ يمنع إثبات الحيازة حتى إدخال المرجع |
| كمية صفر/سالبة/غير رقمية | رفض |
| سعر صفر/سالب | رفض |
| خصم أو ضريبة خارج 0–100 | رفض |
| صنف غير موجود أو مكرر في نفس الحمولة | رفض |
| عملة متصفح مختلفة | لا يقبل RPC عملة العميل؛ يستخدم `app_settings.currency` |
| نفس operation_id ونفس المحتوى | نفس الفاتورة |
| نفس operation_id ومحتوى مختلف | رفض |
| مسودة Quick Market جديدة | لا تغيير في `stock_branches` أو `inventory_log` أو `supplier_ledger` أو `journal_entries` أو `treasury` |

### 2.3 دفتر الحيازة

| الاختبار | النتيجة المتوقعة |
|---|---|
| المورد ← Buyer لكمية 2.5 | حدث موجب 2.5 للصنف |
| المركبة = NULL | نجاح؛ المركبة ليست شرطًا |
| نفس العملية ونفس الحمولة | duplicate=true دون حدث جديد |
| نفس العملية وحمولة مختلفة | رفض |
| كمية أكبر من كمية الفاتورة المتبقية | رفض |
| صنف ليس في الفاتورة | رفض |
| مستخدم آخر يحاول التسجيل | رفض إلا صاحب الفاتورة والمخوّل |
| قراءة الرصيد | مجموع `qty_delta` للأحداث؛ لا يوجد رصيد قابل للتحرير |
| تعديل/حذف حدث مباشر | رفض بواسطة trigger والمنح |
| محاولة استدعاء قراءة كل الموظفين من مشتريات عادي | يرى نفسه فقط |
| المالية المخولة | ترى النطاق الشامل |

### 2.4 حماية العهدة النقدية

| الاختبار | النتيجة المتوقعة |
|---|---|
| عهدة لم يؤكد الموظف استلامها | لا تستخدم لحجز Quick Market |
| عهدة بعملة مختلفة | رفض |
| فاتورة Quick Market أكبر من النقد المتاح بعد الحجوزات | رفض |
| عمليتا إنشاء متزامنتان على نفس العهدة | قفل سجل العهدة يمنع تجاوز مجموع الحجوزات |
| تعديل المسودة إلى مبلغ أكبر من المتاح | رفض |
| تغيير مصدر التسوية إلى Supplier Credit | لا يحجز عهدة نقدية ولا يقبل cash_custody_id |
| وجود مسودة Quick Market | تخفض «المتاح» في Buyer وCustody |
| PO invoice ائتمانية | لا تخصم من عهدة نقدية لمجرد الإنشاء |

ملاحظة: مرحلة Buyer الأولى لا تقدم مصروف Quick Market إلى المالية؛ الحجز يمنع الإنفاق فوق العهدة، أما تقديم المصروف واعتماده فينتظر ربط فاتورة السوق باستلام Receiver المقبول.

### 2.5 حارس الترحيل ومصدر الأثر

| الاختبار | النتيجة المتوقعة |
|---|---|
| POST_INVOICE على Quick Market | رفض واضح يتطلب Receiver |
| POST_INVOICE على PO دون استلام | رفض من الوظيفة المركزية القائمة |
| POST_INVOICE على PO بعد استلام صحيح | يمر عبر `purchase_post_invoice_atomic` القائم فقط |
| تكرار POST_INVOICE | duplicate دون قيد أو حركة إضافية |
| PO receipt | الكاتب الوحيد لحركة PurchaseIn والتزام AP/GL كما هو حاليًا |
| Quick Market Draft أو handover | لا stock/AP/GL/cash posting |

## 3. معاملات اختبار بلا بيانات دائمة

يجب تنفيذ اختبارات الإنشاء والحيازة بعد نشر SQL المعتمد فقط، ضمن معاملة واحدة تنتهي بـ `ROLLBACK`، وبـJWT مستخدم مصرح به. الهيكل المطلوب:

```sql
BEGIN;
SET LOCAL lock_timeout = '2s';
SET LOCAL statement_timeout = '20s';

-- استخدم JWT لمستخدم مشتريات اختباري/مصرح به من الشركة نفسها.
-- لا تستخدم بيانات فاتورة قديمة ولا تحفظ أي صف خارج المعاملة.
-- 1) SELECT purchase_create_quick_market_invoice_atomic(...);
-- 2) SELECT buyer_goods_custody_get_invoice_handover_progress_atomic(...);
-- 3) SELECT buyer_goods_custody_register_handover_atomic(...);
-- 4) أعد نفس استدعاء الحيازة بنفس operation_id والحمولة.
-- 5) اختبر التناقض باستخدام operation_id نفسه وحمولة مختلفة داخل DO/EXCEPTION.
-- 6) قارن counts وbalances قبل وبعد استدعاء الإنشاء والحيازة.

ROLLBACK;
```

لا يجوز وضع `COMMIT` داخل ملف الاختبار. إن انتهت المعاملة بسبب أي خطأ، يجب أن تكون النتيجة صفر بيانات دائمة.

### 3.1 بصمة الأثر قبل/بعد

قبل الاختبار وبعده داخل المعاملة نفسها، سجّل:
- عدد صفوف `purchase_invoices`.
- عدد صفوف `buyer_goods_custody_events`.
- عدد صفوف `inventory_log`.
- عدد صفوف `supplier_ledger`.
- عدد صفوف `journal_entries`.
- أرصدة `stock_branches` للصنف والفرع المستخدمين.
- `treasury.current_balance` للخزينة.
- `buyer_custodies.issued_amount` وحركات السلف.

الفرق المتوقع بعد الإنشاء/الحيازة قبل Receiver: لا فرق في أي من أرصدة المخزون أو المورد أو الأستاذ العام أو الخزينة. يضاف حدث حيازة فقط داخل المعاملة، ثم يختفي عند ROLLBACK.

## 4. اختبارات واجهة Buyer

بعد نشر المصدر والوظائف المتوافقة:
1. تحميل Buyer من النسخة المنشورة ومقارنة byte/hash مع Git blob.
2. مستخدم المشتريات يرى PO وQuick Market بوضوح منفصل.
3. نموذج PO لا ينشئ فاتورة جديدة بلا PO.
4. Quick Market يعمل بلا PO.
5. نتائج بحث الصنف لا تعرض `cost_price` ولا تستخدمه كقيمة افتراضية.
6. السعر الفعلي مطلوب لكل بند.
7. اختيار عهدة نقدية يعرض الرصيد المتاح بعد الحجوزات، لا بعد المصروفات فقط.
8. إثبات المورد → Buyer يسمح بكمية جزئية ومركبة فارغة.
9. إعادة المحاولة بنفس المفتاح لا تكرر حدث الحيازة.
10. «فواتيري» يعرض فواتير المستخدم الحالي افتراضيًا؛ عرض الشركة يتطلب صلاحية مالية.
11. رصيد الحيازة يقرأ دفتر الأحداث وليس مخزون المركبات.
12. عدم ظهور أي زر يؤدي إلى زيادة مخزون الفرع من Buyer.

لا يُشغّل اختبار حفظ من المتصفح على Production إذا كان سيترك حدثًا دائمًا في دفتر append-only. اختبار الواجهة المصادق عليه في هذه المرحلة يختبر النماذج والتحقق وطلبات القراءة؛ أما مسار الكتابة فيُختبر ضمن معاملة SQL تنتهي بـ ROLLBACK إلى أن يعتمد مسار QA مؤقتًا قابلًا للعكس.

## 5. اختبارات المراحل المؤجلة

### 5.1 Receiver — مرحلة لاحقة حسب قرار المالك

- استلام PO مباشر من المورد.
- استلام فاتورة Quick Market بلا PO.
- موظف الاستلام المخول فقط وبحسب الفرع.
- المقبول والمرفوض لكل بند، واستلام جزئي وعشري.
- منع الاستلام الصفري أو الزائد أو المكرر.
- المخزون يزيد بالمقبول فقط.
- Quick Market المقبول يخصم من عهدة البضاعة لدى Buyer.
- تلتزم المالية بمقدار القبول فقط، مع معالجة الكمية المدفوعة/غير المقبولة كرصيد مطالبة/دفعة مقدمة بحسب مستند التسوية الفعلي.
- PO receipt يبقى الكاتب الوحيد لدائن المورد؛ فاتورة PO لا تنشئ دائنًا ثانيًا.

### 5.2 SupplierReturn — مرحلة مستقلة

- إرسال مخزون مرتجع مرة واحدة فقط.
- مسار Supplier Direct لا ينشئ حيازة Buyer.
- مسار Buyer Delegate ينشئ حدث حيازة موجبًا داخل معاملة الإرسال.
- قبول المورد على دفعات وبنود مع إيصال استلام.
- تخفيض AP والضريبة بالقيمة المقبولة فقط، لا بإجمالي الإذن.
- المرفوض يبقى في حيازة Buyer أو يعود للمخزن بمستند.
- لا يجوز أن يعمل `purchase_post_return_atomic` ككاتب مخزون ثانٍ لمرتجع مرتبط بقسيمة أرسلت بالفعل.

### 5.3 العهدة النقدية

- التسليم والزيادة لا يصبحان صرفًا إلا بعد تأكيد الموظف.
- مصروف Quick Market لا يعتمد قبل وجود مستند Receiver مرتبط بالفاتورة وبنودها.
- إن دفع Buyer للمورد نقدًا قبل الاستلام، يجب أن تُعالج القيمة غير المقبولة كمطالبة/دفعة مقدمة للمورد أو تسوية أخرى معتمدة، ولا تختفي كفرق مصروف.
- إن تجاوزت المصروفات النقد المسلم، لا يصنف `amount_due_employee` كمدفوع أو مسوى قبل حساب دائن موظف معتمد وسند دفع حقيقي.

## 6. قبول التكامل

تعتبر المرحلة الأولى ناجحة فقط عند تحقق جميع ما يلي:
- المصدر والنسخة المنشورة متطابقان.
- SQL/RPC/Edge/UI يستخدمون أسماء العمليات والحقول نفسها.
- لا يوجد مسار متصفح يكتب مباشرة في دفتر الحيازة.
- EGP مأخوذة من إعدادات النظام الأم.
- لا تُنشأ حركة مخزون أو AP أو GL أو صرف خزينة بسبب إنشاء الفاتورة أو handover.
- حيازة الصنف مشتقة من أحداث متتابعة لا من رصيد قابل للتحرير أو مركبة إلزامية.
- إعادة المحاولة لا تكرر الأثر.
- لا تزال الفواتير التاريخية SAR كما هي.
- نجاح اختبار المعاملة مع ROLLBACK وعدم تغير أي baseline بعد الخروج منها.
- نشر Cloudflare والاختبار المصادق عليه وتدقيق Network/Console مكتملان.

## 7. التراجع

- الرجوع عن Buyer والـEdge أولًا إلى نسختهما السابقة.
- التحقق أن لا أحداث حيازة ولا فواتير مصنفة جديدة ولا سجلات عمليات جديدة.
- تشغيل ملف `06_buyer_phase1_guarded_rollback_REVIEWED_DRAFT.sql` فقط إذا اجتازت شروط الحماية.
- إذا وُجدت أحداث حيازة أو فواتير مصنفة، يتوقف التراجع؛ لا تحذف أحداث append-only ولا تعكسها آليًا.
- لا يلمس التراجع صفوف الفواتير التاريخية أو حركات المخزون أو دفتر المورد أو القيود أو الخزينة.
