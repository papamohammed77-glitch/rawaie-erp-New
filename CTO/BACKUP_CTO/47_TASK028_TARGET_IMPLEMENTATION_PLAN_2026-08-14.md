## FACT

Production evidence confirms:

- `post_stock_movement(...)` exists as a `SECURITY DEFINER` PostgreSQL function and currently excludes `Loading` / `Unloading` from its closed movement list.
- `complete-loading` currently performs direct `stock_branches` mutation, direct `inventory_log` insertion, direct `run_sheet_details` mutation, accounting, order status changes, and Backorder side effects in sequential calls.
- `unload-runsheet` currently restores MAIN directly and does not decrement the Vehicle/VAN stock branch.
- `sync_run_sheet_details()` is an `AFTER INSERT OR DELETE OR UPDATE` trigger on `order_details` and aggregates `qty`, `qty_picked`, `qty_loaded`, `qty_delivered`, `qty_refused`, `qty_returned`, and driver liability into `run_sheet_details`.
- The live `run_sheet_details` schema does not expose the legacy `remaining_qty` field referenced by the current `complete-loading` function.
- Vehicle `VEH-92yrzb` has a corresponding production branch `VAN-VEH-92yrzb`.

## DECISION

Principal CTO authorization in the controlling directive is accepted.

```text
Loading   = internal MAIN -> VAN stock transfer
Unloading = exact inverse VAN -> MAIN
Loading   != DirectSale
Loading   != Customer Return
No COGS at Loading
```

## TARGET

### Loading

A single database transaction will:

1. lock the Runsheet;
2. require `status = Loading`;
3. resolve the assigned Vehicle and its canonical `VAN-<vehicle_code>` branch;
4. validate each requested item against `order_details` picked capacity;
5. lock MAIN and VAN stock rows in deterministic order;
6. move stock MAIN -> VAN;
7. release the corresponding MAIN allocation;
8. distribute `loaded_qty` across the matching order lines without exceeding each line's picked quantity;
9. allow the existing `sync_run_sheet_details()` trigger to derive Runsheet aggregates;
10. write exactly one deterministic Loading inventory event per item;
11. create one Backorder ledger record per still-unfulfilled order detail where required;
12. transition Runsheet `Loading -> Loaded`;
13. transition linked Orders to `Loaded`;
14. commit atomically.

### Unloading

A single database transaction will:

1. lock the Runsheet;
2. require `status = Loaded`;
3. resolve the Vehicle/VAN branch;
4. read the persisted aggregate `qty_loaded` from `run_sheet_details`;
5. lock VAN and MAIN stock rows in deterministic order;
6. move VAN -> MAIN using exact persisted loaded quantities;
7. write exactly one deterministic Unloading inventory event per item;
8. reset `order_details.qty_loaded` to zero, allowing the existing trigger to derive the Runsheet state;
9. cancel Backorder ledger rows generated by the reversed loading event;
10. transition Runsheet `Loaded -> Picked`;
11. transition linked Orders to `Pending` (the status used by the current Runsheet creation workflow);
12. commit atomically.

## UNKNOWN

- No production Backorder table exists. A small internal ledger table is therefore introduced in the migration, rather than inventing automatic child Orders inside the Loading transaction.
- COGS remains explicitly excluded from Loading. Sales/Delivery accounting remains outside this surgical change.

## IDEMPOTENCY

The primary idempotency guard is the locked Runsheet state:

```text
first successful call: Loading -> Loaded
retry after commit: status is Loaded -> reject without stock effect
```

Because the stock, logs, order quantities, Backorder records, and state transition are inside one PostgreSQL transaction, a failure rolls the entire operation back.

No `Date.now()` or random number is used for business-event identity.

## ATOMICITY

The Loading and Unloading RPCs are the transaction boundary. Edge Functions become capability wrappers only.

## TRIGGER BOUNDARY

`order_details` is authoritative for the fulfillment quantities. `sync_run_sheet_details()` remains the aggregation layer. The new Core RPC does not manually write `run_sheet_details`.

## CORE RPCS

```text
public.complete_runsheet_loading(uuid, uuid, jsonb, text)
public.complete_runsheet_unloading(uuid, text, text)
```

The first RPC accepts item-level loading requests in JSON form:

```json
[
  {"item_code":"ITEM-001","loaded_qty":6}
]
```

The capability wrapper preserves the existing client-facing field names (`itemCode`, `loadedQty`).

## BACKORDER LEDGER

`public.fulfillment_backorders` is a durable queue/ledger for unfulfilled order-detail quantities generated by the current Loading event.

It is deliberately not a new customer Order. This prevents automatic order duplication while preserving:

- original order;
- original order detail;
- originating Runsheet;
- remaining quantity;
- lifecycle status.

A later Backorder workflow can consume this ledger under its own contract.

## FAILURE ROLLBACK

The transaction must reject and roll back on:

- missing Vehicle;
- missing VAN branch;
- missing stock row;
- insufficient available stock;
- loaded quantity exceeding picked capacity;
- invalid item/company context;
- invalid Runsheet state;
- inventory log failure;
- order detail update failure;
- state transition failure.

## ACCOUNTING

No `journal_entries` or `journal_lines` are created by the Loading/Unloading Core.

Loading is an internal inventory transfer.
